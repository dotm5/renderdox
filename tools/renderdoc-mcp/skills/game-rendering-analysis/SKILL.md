# 游戏渲染分析

由 LLM 选择调查路径、解释算法、组织图片和撰写文章；MCP 提供原始数据和可复查的实验结果。**默认从捕获中主动寻找有趣、特化或值得复用的渲染思路，再选择有价值的候选深入分析，不等待用户逐项点名。** 不将调查限制为预设效果名称，也不要求每个普通 Pass 都精细拆解。用户明确指定组件时优先回答专项问题；“以角色为例”仍可追踪影响其表现的场景光照和后处理。

## 默认模式：启发式发现

先建立粗粒度的事件、输出和资源关系概览，再从实际证据发现候选。以下只是启发方向，不是必查清单、分类边界或深入分析的准入条件：

- 光照与表面：SSS/透射、特殊阴影、AO、反射、非标准 BRDF、卡通光照、MatCap、描边。
- 几何与空间：顶点置换、曲面细分、视差/POM、特殊蒙皮或变形；区分真实几何变化和 UV/法线造成的视觉效果。
- 材质叠加：湿润、水滴、积雪、溶解、贴花、透明/折射、自发光及其他特殊分层。
- 屏幕后处理：Bloom、景深、运动模糊、抗锯齿、曝光、Tone Mapping、调色 LUT、颜色编码与最终显示转换。
- 支撑机制：深度/法线等中间缓冲、光照列表、阴影图和跨 Pass 合成关系。

尤其关注异常或有辨识度的信号：特殊资源格式/维度/数组、非典型缓冲复用、反复出现的采样或计算结构、意外的混合/深度状态、几何变化、局部视觉特征、跨 Pass 数据传递，以及普通名称下的特殊实现。名称常见的 Pass 也可能值得拆；无法命名的机制先用证据描述，不能强行套成已知效果。

建立可迭代的候选笔记，记录发现信号、证据锚点、可能机制、值得研究的原因和验证问题。根据视觉贡献、实现独特性、复用价值、证据可得性选择深入对象；选择由 LLM 判断，不设固定数量或固定效果列表。调查过程中发现新机制可改变优先级。保留暂未深入的有价值候选及理由，不把有限调查写成全部机制已穷尽。取数分批、按需、去重，不调试每个 draw 和像素。

## 加载与能力判断

- 调用 `get_capabilities`；已有 RDC 时直接 `open_capture`，当前实例时使用现有连接捕获。确认捕获身份、API、分辨率、帧号及回放状态。
- 工具的具体参数以本服务 `tools/list` 为准。异步操作拿到 `jobId` 后用 `get_job` 等待终态，检查错误及结果完整性。
- 按需读 [工具路由](references/tool-routing.md)。MCP 客户端可用 `get_analysis_skill(name="game-rendering-analysis", path="references/tool-routing.md")` 读取；同名相对引用也列为 MCP resource URI。
- 制定实验前读 [回放实验](references/replay-experiments.md)；写文章时读 [文章格式](references/article-format.md)；判断是否能自动完成时读 [能力边界](references/capability-audit.md)。不一次加载所有参考文件。

## 1. 从整帧概览建立组件与调查对象

默认先从最终输出逆向跟踪主要渲染阶段，并结合事件顺序、资源生产/消费、Shader 家族和画面贡献发现候选。将发现转成可观察的问题，例如某个不寻常的查表、几何变形或多阶段合成怎样产生画面特征。再选择代表性区域、像素或输出目标，保存全景定位图和局部放大图。专项请求可以直接从指定组件开始。

用 `get_capture_summary`、`find_actions`、`get_pipeline_state` 和 `get_draw_evidence` 建立有限候选。从 `locate_draws_at_pixel` 的真实写入与失败原因、`visualize_draw_contribution` 的变化区域确认归属。差分针对哪个目标就只说明该目标；不要称为整角色分割。

## 2. 两层归组，分别解决几何和效果

**绘制家族**：用 `group_related_draws` 查找同几何的深度、阴影、主绘制、描边候选，再用变换/蒙皮常量、材质绑定和屏幕贡献复核。相同网格或 Shader 不自动等于同一对象。用资源流和输出状态推断 Pass；没有 marker 时标为分析者命名。

**Shader 内部模块**：对同一绘制内的颜色、法线、阴影、粗糙度、高光、湿润、自发光和后处理逐项追踪输入及消费点。水滴可以是一个 Shader 分支，不能因为没有新增 draw 就说没有叠加。聚簇光照的 light-list/grid 是另一个待分析算法，不等同于绘制聚类。

## 3. 用输入和数据流解释算法

对每个待解释效果记录：纹理槽/数组层/mip、采样器、常量块及偏移、坐标空间、条件分支、写入目标、指令范围、当前帧参数和可见作用。

用 `get_shader` 的反射和反汇编、`get_constants`、`read_texture`、`get_buffer_data` 与资源预览作来源；用 `debug_shader`、`query_shader_trace` 检查代表性点的输入、中间寄存器及实际分支。调试轨迹不完整或变量是 Unknown 时保留缺口，不能猜一个 float 类型后声称数值证明。

LLM 将计算重写成分模块 HLSL，保留资源/寄存器到语义名的对应表。代码标注为：原始源代码（只有确有源码时）、经回放验证的等效重建、或说明性伪代码。DXBC 反汇编不是原始 HLSL；编译通过也不等于输出等价。核对矩阵行列、空间、符号、法线混合、采样 LOD、颜色编码和 MRT 输出契约。

## 4. 为关键解释设计最小实验

给出简短的假设、观察方法、预期差异和实测结果。已有数据可以回答时不增加实验；需要因果证据时按实验参考进行离线回放，避免改变运行中的游戏。

优先保存原始基线、单项禁用、单项输出、最终合成及 ROI 差分。重建 Shader 未能复现基线时，先报告近似误差，再决定是否继续。共享 Shader 的替换影响多个绘制，明确影响范围。

雨痕示例：先确认湿度分支及时间输入，再跟踪动画 UV → 覆盖遮罩 → 法线扰动 → AO/粗糙度 → 高光 → 合成。分别检查“材质参数混合、同网格附加绘制、贴花、屏幕处理”的证据；不要预设某一种实现。只有干燥帧或未执行分支时，可以描述代码路径，但不能把潜在功能写成当前可见效果。

## 5. 组织成可读文章并积累证据

按 [文章格式](references/article-format.md) 写全景、流程概览及候选选择依据，再深入解释选中的渲染思路。每一节以现象或问题起笔，连接输入图、精简 HLSL、内部量、开关实验和结论；未完成项留在“待验证”，不补造图片。

用 `annotate_capture` 保存效果名称、候选关系、已确认结论、未确认问题和证据定位；复用时按捕获哈希/格式/绑定/字节码复核，不能复用旧 EID 的含义。将 MCP 原始证据通过 `export_analysis_bundle` 保存；LLM 在宿主文件工具中生成文章、代码和解释图，维持相对链接及可追溯出处。

## 完成标准

- 默认任务说明观察范围、发现线索、深入对象及选择理由，保留有价值但未深入的候选和证据缺口；不以固定类别覆盖率作为完成条件。专项任务回答指定范围及必要上下游。
- 当前实例/捕获及证据范围明确，主要结论可追溯至 EID、资源、常量、指令或实验。
- 图片区分原值、通道视图、显示预览、差分和解释图，颜色转换有记录。
- 确认、推断、未知与精确、近似分开标注；存在于字节码的功能和当前执行效果分开。
- HLSL 有来源与验证状态；实验保存基线、影响范围、误差、恢复结果。
- LLM 撰写的文章可脱离工具日志阅读；原始数据包用于复查。

## 使用示例

- “分析这份 RDC 的渲染机制”：广泛观察，从实际捕获发现值得拆解的思路，自主选择深入对象并交付图文解释与有验证状态的 HLSL。
- “以这份 RDC 的角色为例，图文解释脸部阴影和描边，给出等效 HLSL。”
- “分析皮肤水滴的覆盖、法线、粗糙度和高光如何叠加；没有湿润帧时指出需要哪些补充捕获。”
- “按知乎渲染分析文章的形式组织已有证据，保留未经验证的解释。”
